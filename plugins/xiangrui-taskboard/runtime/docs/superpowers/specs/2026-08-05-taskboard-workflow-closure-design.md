# xiangrui Taskboard 执行与返工闭环设计

日期：2026-08-05
状态：采用推荐方案进入实施，实际效果待祥瑞验收

## 背景

当前任务面板同时提供评论、在 Codex 中打开、评论并交给 Codex、自动认领、工作流和重复等入口，但这些入口并不共享一套清晰的执行语义。最明显的问题是：评论只写入记录，不改变议题状态，也不会触发 Codex；处于审核中的议题收到反馈后，仍停留在审核中，因此自动认领永远看不到这条返工要求。

本设计不引入新的执行队列或大规模后端重构，优先复用现有评论、状态、负责人和 Codex 任务创建能力，把真实主路径接通。

## 目标

1. 让评论、返工、即时交办和自动认领各自有明确且不重叠的含义。
2. 让审核反馈能够可靠回到待办，并可选择立即交给 Codex。
3. 让自动认领只领取明确交给 Codex、当前可执行的议题。
4. 让执行成功、失败和暂停都有可见结果，不把议题永久留在进行中。
5. 隐藏尚无执行器的功能，避免界面承诺不存在的能力。

## 非目标

1. 本轮不新增独立的 run、job 或 execution_request 数据表。
2. 本轮不实现真正的周期议题生成器。
3. 本轮不实现工作流节点执行引擎。
4. 在祥瑞确认主路径实际可用前，不进行无关重构、兼容层扩张或大规模测试改造。

## 当前真实操作链路

### 普通评论

入口是 `web/src/components/TaskDetail.tsx` 的评论编辑器。`submitComment(false)` 调用 `web/src/api.ts` 的 `createComment()`，后端由 `server/app.mjs` 的 `/api/tasks/:taskId/comments` 路由写入 `server/database.mjs` 的 `comments` 表。可观察结果只有评论列表新增一条记录，没有任何任务状态变更。

### 评论并交给 Codex

同一组件中的 `submitComment(true)` 先保存评论及附件，成功后调用 `onOpenInThread(currentTask, { autoSubmit: true })`。`web/src/App.tsx` 的 `openTaskInThread()` 向宿主发送 `taskboard:create-thread`，注入层在 `inject/codex-taskboard.user.js`、`scripts/codex-injector-runtime.mjs` 和 `scripts/codex-injector.mjs` 中创建并提交原生 Codex 任务。Prompt 通过 `manage-taskboard` Skill 指示 Agent 重新读取议题和全部评论。

当前缺口是：这条路径不会先把审核中的议题退回待办，而且向 Codex 交办时仍使用操作前的任务快照。

### 自动认领

`web/src/components/ProjectAutomationMenu.tsx` 保存项目级设置，`web/src/App.tsx` 解析 Taskboard 项目与 Codex 项目的目录映射，`shared/taskboard-automation.mjs` 生成周期自动化 Prompt，并由宿主创建或更新 Codex automation。

当前 Prompt 只要求“每次处理一个 todo”，没有限定负责人、阻塞关系和稳定排序；失败时也没有明确恢复规则。因此它可能认领属于人的任务，也可能把失败议题留在进行中。

### 仅保存但未执行的能力

`workflowId` 与 `recurrence` 当前只在表单、API 和数据库中保存。项目没有议题工作流执行器，也没有生成下一条周期议题的调度器。`web/src/App.tsx` 已用 `SHOW_WORKFLOW_BOARD_ENTRY = false` 隐藏部分工作流入口，但议题详情仍可绑定工作流和重复设置。

## 统一交互语义

### 四种动作

| 动作 | 保存评论 | 改变状态 | 启动 Codex |
| --- | --- | --- | --- |
| 评论 | 是 | 否 | 否 |
| 提交修改意见 | 是 | `in_review` → `todo` | 否 |
| 立即返工 | 是 | `in_review` → `todo` | 是 |
| 交给 Codex | 可无评论 | 保持或进入 `todo`，由 Agent 认领时进入 `in_progress` | 是 |

评论是项目记录，状态变化和执行是显式动作。按钮文字必须能准确预告副作用。

### 状态对应行为

| 当前状态 | 评论区主动作 | 次动作 | 结果 |
| --- | --- | --- | --- |
| 待整理 `backlog` | 评论 | 加入待办 | 进入 `todo` |
| 待办 `todo` | 评论 | 交给 Codex | 立即创建 Codex 任务 |
| 进行中 `in_progress` | 评论 | 在 Codex 中查看 | 评论仅保存，并提示当前运行不一定实时读取新评论 |
| 审核中 `in_review` | 提交修改意见 | 立即返工 | 默认退回 `todo`；立即返工额外创建 Codex 任务 |
| 已阻塞 `blocked` | 评论 | 解除阻塞并进入待办 | 由人明确决定后进入 `todo` |
| 已完成 `done` | 评论 | 重新打开 | 进入 `todo` |

本轮核心主路径是 `in_review` 的“提交修改意见”和“立即返工”。其他状态入口沿用现有属性修改能力，逐步统一文案，不新增复杂状态机服务。

## 核心数据顺序

### 提交修改意见

1. 保存评论正文与附件。
2. 附件全部保存成功后，使用议题最新 version 将状态更新为 `todo`。
3. 更新成功后清空编辑器，并在界面显示“修改意见已提交，议题已退回待办”。
4. 如果评论已保存但状态更新失败，保留评论并明确提示“评论已保留，但退回待办失败”，禁止假装整个动作成功。

### 立即返工

1. 完成“提交修改意见”的全部步骤。
2. 使用更新后的任务快照创建原生 Codex 任务并自动提交。
3. Codex Agent 通过 `manage-taskboard` 重新读取议题和全部评论，再用最新 version 认领为 `in_progress`。
4. 如果创建 Codex 任务失败，议题仍保留在 `todo`，评论也保留，用户可重试，不产生丢失。

## 自动认领规则

自动化 Prompt 必须明确：

1. 只处理状态为 `todo` 且负责人为 `Codex Agent` 的议题。
2. 跳过存在未完成阻塞关系的议题。
3. 候选排序固定为：优先级、截止时间、看板顺序、创建时间。
4. 每轮只处理一条，认领前重新读取议题和全部评论。
5. 使用最新 version 从 `todo` 原子移动到 `in_progress`；冲突就跳过。
6. 成功后写执行评论并移动到 `in_review`，不直接完成。
7. 失败后写明原因和建议，将议题移动到 `blocked`，不永久停在 `in_progress`。

负责人字段已经由 `assigneeTarget` 支持 `current-user` 与 `codex-agent`，因此无需新增表字段。

## 执行退出与人工验收

`in_progress` 只表示 Codex 当前确实正在处理，不能成为停止运行后的默认停放区。Agent 在能够正常收尾时，必须按原因选择唯一出口：

1. 已完成并自检通过：写结果评论，进入 `in_review`。
2. 临时中断但任务仍有效、重新执行即可继续：写明中断点，退回 `todo`。
3. 缺少资料、等待祥瑞决定或被未完成依赖阻塞：写明解除条件，进入 `blocked`。
4. 明确不再处理：只有祥瑞可以决定进入 `canceled`，Agent 不自行取消。
5. 不论自动化还是即时交办，都不能因为自检通过而直接进入 `done`。

周期自动化可以辅助回收异常退出的 `in_progress`，但必须先通过关联 `threadId` 确认对应 Codex 任务已经失败或中断。禁止仅根据更新时间推断任务已停止，也禁止重置仍在运行的任务。无法确认运行状态时保持原状并等待人工处理。

`in_review` 继续表示祥瑞正在审核。祥瑞验收通过后才进入 `done`；不通过时使用“退回修改”或“退回并立即处理”。本轮不增加自动完成，也不让 Agent 自己批准自己的交付。

## 自动化状态与项目映射

自动化入口不再用一个“无自动化”概括所有情况，而是区分：

1. 未启用
2. 已暂停
3. 额度不足，已暂停
4. 额度状态未知，已暂停
5. 项目未映射
6. 运行中

项目映射继续以本地绝对目录为权威。Taskboard 项目 ID 与 Codex Project ID 不同时，`web/src/App.tsx` 应通过目录路径寻找对应 Codex 项目；找不到时显示具体原因和设置动作，而不是只禁用开关。

## 未完成能力收口

1. 从议题详情和新建议题表单隐藏“重复”，保留数据库字段以兼容已有数据。
2. 从议题详情和新建议题表单隐藏“工作流绑定”，保留现有工作流代码和数据，不在本轮删除。
3. 删除或隐藏没有实际处理价值的隐藏列入口，但不删除已保存的列配置。
4. 将浮动 AI Chat 明确命名为“面板助手”，只负责查询、整理和修改面板，不将其描述为议题执行入口。

## 可观察结果

主路径完成后，祥瑞应能直接看到：

1. 审核中议题的评论按钮变为“提交修改意见”。
2. 点击后评论出现，议题从审核中移到待办。
3. 点击“立即返工”后，评论出现、议题进入待办，并创建一个已提交的原生 Codex 任务。
4. 普通“评论”仍只保存记录，不会暗中启动 Codex。
5. 自动化入口显示准确状态；自动认领说明明确只认领 Codex Agent 的待办。
6. 工作流和重复不再以可用功能出现在议题界面。
7. Agent 正常退出时不会把议题遗留在进行中；异常中断只有在确认关联任务已停止后才回收到待办或阻塞。

## 验证方式

遵循仓库 `AGENTS.md`：先证明真实操作路径，再验证这条直接路径，不在祥瑞确认前扩张保护性测试。

1. 在实际运行的 Taskboard 中准备一条 `in_review` 议题。
2. 用“提交修改意见”发布一条可识别的评论，观察评论和状态变化。
3. 再准备一条 `in_review` 议题，用“立即返工”发布评论，观察状态和原生 Codex 任务提交。
4. 检查自动化菜单的状态文字及项目映射提示。
5. 检查工作流、重复和隐藏列入口不再误导。
6. 记录实际结果交给祥瑞确认；确认后再补充必要的回归保护。

## 风险与恢复

1. 评论保存与状态更新不是数据库事务。采用“评论优先、失败可见、状态可重试”的顺序，保证要求不丢失。
2. 原生 Codex 任务创建依赖项目映射。映射失败时议题停留在 `todo`，不回滚已保存的评论。
3. 自动化仍依赖 Prompt 执行协议，不具备独立运行队列的强一致性。若后续出现重复执行、任务卡死或重试需求，再升级为独立 execution run 模型。
